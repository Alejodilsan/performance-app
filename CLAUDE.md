# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository: **AlemiaHR**, a Next.js + Supabase HR performance-management app (multi-tenant).

## Overview

All UI text, identifiers, table names and commit messages are in **Spanish**; keep new code consistent with that.

### Commands

```bash
npm run dev     # dev server on http://localhost:3000
npm run build   # production build (also the de-facto type check)
npm run lint    # eslint (next core-web-vitals + typescript configs)
```

There is no test suite.

Requires `.env.local` with `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` (the last is server-only, used by the `/api` routes).

### Stack

Next.js 16 (App Router) · React 19 · TypeScript (strict) · Tailwind CSS v4 (via `@tailwindcss/postcss`, no tailwind config file) · Supabase JS v2 · Recharts · `exceljs` for Excel import/template export (`xlsx` was removed for security — don't re-add it). Fonts via `next/font`: Inter (text), Montserrat (titles), Plus Jakarta Sans (logo only). Path alias `@/*` → project root.

### Architecture

- **`app/page.tsx`** (~1,550 lines, `'use client'`) is the `DashboardPerformance` root component: it owns all state and the client-side Supabase writes that are still allowed, and passes data and callbacks down as props (e.g. the `FuncionesTarjeta` bundle given to employee cards). Navigation is not routed: a `vista` state (`'tablero' | 'organigrama' | 'informes' | 'mi_perfil' | 'evaluaciones' | 'okr' | 'estructura'`) switches what is shown. The home (`tablero`) has two tabs: **Mi equipo** (`components/inicio/MiEquipo.tsx` + pure `lib/equipo.ts`: people hierarchy with level-by-level zoom and breadcrumbs; each card shows the person's compliance for the current month with trend, and for leaders their direct-team and whole-branch averages and KPIs pending; "Ver KPIs" opens the full card in a side panel, editable only for direct reports; Admin/Auditor who lead nobody start at the leaders of the root areas) and **Por áreas** (the area tree). "Direct reports" always use `reportesDirectos` from `lib/alcance.ts`, the same rule as the scope. Admin structure tools (new area, cargos, new collaborator, "sin área" tray, desvinculados) live in the `estructura` view.
- **`components/`** holds the presentational pieces, one file each with named exports (`TarjetaEmpleado`, `TarjetaSaludArea`, `MatrizNineBox`, `ModalEvaluacionPotencial`, `ModalPerfilColaborador`, `Organigrama` (`construirArbol` + `NodoOrganigrama`), …). They don't talk to Supabase themselves.
- **`lib/tipos.ts`** holds the shared domain types (`Empleado`, `Area`, `Indicador`, `Perfil`, `FuncionesTarjeta`, …); component prop interfaces live next to their component. The domain type `Area` clashes with recharts' `Area`, so recharts' one is always imported as `Area as RechartsArea`.
- **Data access is mixed.** Simple admin writes (areas, cargos, employees, plans…) go from `app/page.tsx` through the shared anon client in `lib/supabase.ts` (PKCE flow, `detectSessionInUrl`) and rely on Supabase RLS. Everything that depends on scope, permissions or cross-company data goes through the `/api` routes: reads (`/api/datos`, `/api/bi`, `/api/historial`, `/api/okr`, `/api/evaluaciones`, `/api/desarrollo`) and sensitive writes (`/api/resultados`, `/api/pesos`, `/api/periodos`, `/api/okr`, `/api/evaluaciones`, `/api/desarrollo`, `/api/importacion`, `/api/accesos`). Data is scoped by `empresa_id` (multi-tenant). Newer tables (`resultados_kpi`, `periodos_*`, `okr_*`, `ev360_*`, `pdi_*`, `configuracion_empresa`) have RLS with no policies: only the server can touch them.
- **Server code** lives in `app/api/*` (`accesos`, `datos`, `bi`, `desarrollo`, `evaluaciones`, `historial`, `importacion`, `resultados`, `pesos`, `periodos`, `okr`) and uses the service-role key via `lib/servidor/*` (never import `lib/servidor/*` from client code). Admin-only routes (`accesos`, `importacion`, `periodos`, BI config) start with `exigirAdmin(request)`; the rest start with `obtenerContextoSesion(request)` (`lib/servidor/contexto.ts`) and check permissions from `alcance` (exception: `/api/accesos/activar` only validates the caller's own session with `usuarioDesdeRequest`). Both validate the `Authorization: Bearer <jwt>` header and take `empresa_id` from the caller's `perfiles` row — never trust ids sent by the browser. The browser calls them through small clients in `lib/*Api.ts` / `lib/accesos.ts` / `lib/datos.ts`, which attach the session token.
- **Access flow (clave temporal)**: admin selects people in `ModalAccesos` → `/api/accesos` `otorgar` creates the auth user (or resets the password), sets `app_metadata.debe_cambiar_clave = true`, upserts `perfiles`, and returns one-time random passwords. On login, `debe_cambiar_clave` forces `/actualizar-clave`, which then calls `/api/accesos/activar`. `empleados.estado_acceso` tracks `sin_invitar → invitado → activo`. The code is structured so an email-invitation `metodo` can be added later (no SMTP yet).
- **`empleados.tipo_perfil` is the source of truth for permissions**; `perfiles.rol` is derived from it (`lib/roles.ts`) when access is granted and via `sincronizar_rol` when an admin edits the profile type. The API refuses to demote the last admin of a company or to change the caller's own role. Desvincular/reactivar also ban/unban the auth user (`revocar`/`restaurar`).
- **Visibility is hierarchical and computed server-side.** On load the page calls `GET /api/datos` (`lib/datos.ts`), which uses `calcularAlcance` (`lib/alcance.ts`, pure, shared): Admin/Auditor → whole company; anyone who leads an area → that area + all sub-areas (cascade) + people whose `jefe_directo_id` chain leads to them; nobody else → only themselves. Only *direct reports* are editable (`alcance.directosIds`); the cascade is read-only. The API returns full records (KPIs, plans, history) only for people in scope; the org chart gets a minimal `directorio` with no performance data. Upward (ascendente) evaluations about the viewer are never sent to them. Don't reintroduce client-side company-wide queries for non-admins.
- **Page state**: `verificarUsuario()` → `cargarDatos()` fills `perfil`, `alcance`, `empleados` (only the visible people: whole company for Admin/Auditor, otherwise the team in scope), `empleadosDesvinculados` (Admin only), `miDesempeno` (own record), `directorio` and `evaluaciones`. Mutations update `empleados` optimistically and then call `recargarDatos()` (= `cargarDatos()`). Menu: Inicio/Desempeño (BI) for Admin, Auditor or anyone with a team; Mi Perfil, Organigrama, Objetivos (OKR) and Evaluaciones for everyone; Estructura for Admin.
- `app/login/page.tsx` handles login, password recovery, and the "create password" step for invite/recovery links (both `#access_token` hash and `?code=` PKCE variants). `app/actualizar-clave/page.tsx` is a standalone password-update page.

### Key Supabase tables

- Core: `perfiles` (auth user → rol, empresa_id), `empresas`, `areas` (tree via `parent_id`, unique `lider_id`), `empleados`, `configuracion_empresa` (currency, thresholds, grading deadline).
- Cargos: `puestos` (shown as "Cargo"; `area_id`, `nivel_id`), `niveles_cargo`, `rangos_salariales_cargo` (admin-only).
- Performance: `indicadores` (KPIs; `periodo` = frequency, `peso`, `kr_id`), `resultados_kpi` (one result per KPI + month), `historico_cumplimiento` (monthly snapshots, unique on `empleado_id, periodo`; `oficial`), `periodos_cerrados`, `periodos_reaperturas`, `planes_mejora` → `comentarios`, `evaluaciones` (legacy 360, read-only history), `evaluaciones_potencial`.
- 360 cycles: `ev360_competencias` → `ev360_conductas`, `ev360_ciclos`, `ev360_participantes`, `ev360_asignaciones` → `ev360_respuestas`, `ev360_calibraciones`, `ev360_pulsos` → `ev360_pulso_asignaciones` → `ev360_pulso_respuestas`.
- Development (PDI): `pdi_objetivos` → `pdi_acciones`, `pdi_checkins`.
- OKR: `okr_objetivos`, `okr_resultados_clave`.
- People data: `compensaciones` (salary history, admin-only), `historial_empleado` (written only by triggers).

### Domain logic to preserve

- **KPI progress** (`indicadores.progreso`): `direccion = 'creciente'` → `resultado / meta`; `'decreciente'` (lower is better) → 100% if `resultado <= meta`, else `meta / resultado`; clamped to 0–100. The rule lives in `calcularProgreso` (`lib/periodos.ts`). Employee `cumplimiento_general` is the *weighted* average of KPI progress (see **KPI weights**) and is denormalized onto `empleados`; it is recomputed server-side (`lib/servidor/cumplimiento.ts`) whenever a KPI result or weight changes — never compute and save it from the client.
- `potencial_score` (1–3) comes from the multi-dimensional potential evaluation and, together with `cumplimiento_general`, places employees in the Nine-Box matrix.
- **Employees are never deleted.** Leaving the company sets `empleados.estado_contratacion = 'desvinculado'` (+ `fecha_desvinculacion`, `motivo_desvinculacion`) so history is kept. `obtenerDatosCorporativos` splits them out: `empleados` state holds **only active** employees (everything — boards, BI, organigrama, invitations, leader pickers — relies on that), while `empleadosDesvinculados` feeds the admin's "desvinculados" section (view history / reactivate). Desvinculados are signed out on login. Use `estaActivo()` from `lib/tipos.ts` (a missing column counts as active).
- Areas can be hard-deleted by an admin only when they have no active employees, no sub-areas and no cargos.
- **OKR cascade** (`lib/okr.ts`, pure; `/api/okr`; view `components/okr/VistaOKR.tsx`, menu "🎯 Objetivos (OKR)"; migration `20261123_okr.sql`): annual objectives (`okr_objetivos`, `area_id` null = company) with quarterly key results (`okr_resultados_clave`). An area objective must align (`kr_padre_id`) to a KR of the level right above (company for top-level areas, parent area for sub-areas — `validarAlineacion`). KR `medido` has its own target/value; `calculado` = average of linked KPIs (their latest result inside the KR's quarter) and aligned area objectives; objective = average of its KRs in the quarter (`calcularAvance`, recursive). KPIs link via `indicadores.kr_id` (optional: unlinked = "operativo"; the view shows % aligned). Everyone sees all OKRs, but the progress is computed server-side and KPI details are only returned for people in the viewer's scope. Company level: Admin only; area level: Admin or that area's leader (`puedeGestionarNivel`). Tables have RLS with no policies (server only).
- **360 evaluation by cycles** (`lib/evaluacion360.ts`, pure; `/api/evaluaciones`; UI `components/evaluacion360/` (`Vista360` shell, `FormularioEvaluacion`, `InformeIndividual`, `Administrar360`), menu "⭐ Evaluaciones 360"; migration `20261124_evaluacion_360.sql`): a cycle (`frecuencia` semestral/anual, one in progress at a time) moves borrador → nominacion → evaluacion → calibracion → resultados → cerrado, advanced only by the Admin. Launching freezes the questionnaire (`ev360_ciclos.cuestionario` jsonb, so editing the competency library never alters launched cycles), creates one participant per active employee with their 360 leader (`liderDirectoDe`: jefe directo → area leader → nearest ancestor area leader) and the automatic assignments (auto, leader → report, report → leader). **Peers are chosen only by the evaluated person's direct leader** (or Admin). Competencies: `corporativa` for everyone, `liderazgo` only for people with a team (`es_lider`); each behavior is rated 1–5 or "no observado". Result per competency = weighted average of visible perspectives (cycle weights líder/pares/colaboradores, renormalized; **self-assessment never counts**, it only gives the perception gap / Johari quadrant). **Anonymity**: a peer or report group is shown only with ≥ `minimo_anonimato` answers; smaller groups are pooled, and if still below the threshold they are excluded from the score and comments — never send evaluator identities of par/colaborador answers to anyone. Calibration (Admin, `ev360_calibraciones`, with justification) overrides the final score of a competency. The person sees their report **only after their leader registers the 1:1 conversation** (`conversado_en` + `acuerdos`); leaders/Admin/Auditor see team/company reports from calibration on. Submitted evaluations are immutable (trigger). The 360 is **not** part of the Nine Box. The legacy `evaluaciones` table is only shown as "Histórico".
- **Development after the 360** (migration `20261125_desarrollo_360.sql`; pure `lib/desarrollo.ts`; `/api/desarrollo`; UI `components/evaluacion360/Desarrollo.tsx`, tab "🌱 Desarrollo" of the 360 view): each person has up to 3 active PDI objectives (`pdi_objetivos`, optionally tied to a competency of a 360 cycle — suggested from the latest report the viewer may see: blind spots / opportunities first), each with 70-20-10 actions (`pdi_acciones.tipo` experiencia/relacion/formacion). Objective progress is derived (`avanceObjetivo`: 100 if logrado, else % of actions done) — never store it. Monthly check-ins (`pdi_checkins`, one per person + month). Read: the person, their cascade team and Admin/Auditor; edit: the person, their direct leader and Admin. **Pulse** (`/api/evaluaciones` `lanzar_pulso`, Admin, cycle in resultados/cerrado, one per cycle): the same evaluators who completed the 360 rate only the PDI competencies (frozen per assignment); `consolidarPulso` averages all non-self raters only if ≥ `minimo_anonimato`, otherwise shows the leader alone. Server helpers shared by both routes live in `lib/servidor/evaluacion360.ts`. **BI**: `components/bi/Indicadores360.tsx` calls `GET /api/evaluaciones?indicadores=1` with the BI filters; the server returns only aggregates (`agregarIndicadores`; averages need ≥ `minimo_anonimato` people), including the Pearson correlation between the 360 result and `cumplimiento_general`.
- **KPI weights** (`indicadores.peso`): either all null (equal weight) or all > 0 summing 100 (`validarPesos`, saved only via `POST /api/pesos` by Admin or direct leader). Person compliance is a weighted average everywhere (`pesosEfectivos` + `promedioPonderado` in `lib/periodos.ts`; server recompute in `lib/servidor/cumplimiento.ts`, used by `/api/resultados` and `/api/pesos`). `cumplimiento_general` = weighted average of all KPIs' latest progress; monthly compliance = weighted average of the KPIs rated that month.
- **Single leadership** (migration `20261122_liderazgo_unico.sql`): a person leads at most ONE area (`areas_lider_unico_idx`) and belongs to the area they lead (one team only). DB triggers enforce it on every path: setting `areas.lider_id` frees their previous area and moves them (`empleados.area_id`) into the new one; changing a leader's area or desvincularlo clears the area they led. The UI shows the leader on top of the area card / org-chart node, never inside the team list; area metrics still include the leader. The bulk import rejects one person as leader of several areas and a leader whose Colaboradores row puts them in another area.
- The tablero renders areas as a tree (`lib/jerarquia.ts` → `construirJerarquia`, drawn by `components/ArbolAreas.tsx`). `parent_id` must never form a cycle: "Depende de" only offers non-descendant areas and `asignarPadreArea` rejects cycles. The header search (`components/BuscadorGlobal.tsx` + pure `lib/busqueda.ts`) shows a dropdown of matching people and areas with the match highlighted (`resaltar`, accent/case-insensitive; keyboard ↑↓/Enter/Esc, `/` to focus). Picking a person zooms "Mi equipo" to them (highlight + side panel); picking an area opens "Por áreas", reveals its branch and scrolls to it. Typing does not filter anything; only "Filtrar el árbol por áreas" sets `filtroArbol`, which prunes the tree with `filtrarJerarquia` (keeps ancestors for context) and also filters the "sin área" tray and desvinculados.
- Schema changes live as SQL in `supabase/migrations/` and are applied by hand in the Supabase SQL editor (no Supabase CLI in this project).
- **Employee form** (create + edit) is `components/PanelColaborador.tsx` (Área comes before Cargo; cargos of the chosen area are listed first and a quick-created cargo goes into that area), a side drawer with essentials + collapsible sections (laborales, personales, compensación). Its pure logic — defaults, validation, DB payload, money parsing, `opcionesJefeDirecto` (no reporting cycles) — lives in `lib/colaboradores.ts` so the bulk import can reuse it. `jefe_directo_id` is independent of `areas.lider_id` (the form only *suggests* the area leader).
- **Salary is never stored in `empleados`** (that table is readable by non-admins). It lives in `compensaciones`, one row per change (history; current = latest `fecha_vigencia`), protected by RLS via `es_admin_de_empresa()` so only admins of the same company can read/write it.
- **BI module** (`components/bi/`, opened from "Desempeño (BI)"): `PanelBI` loads `GET /api/bi` with the filters (área incl. sub-areas, sede, contrato). Pure logic is in `lib/bi.ts` (Nine Box classification, monthly salary, company cost = base × `factor_prestacional`, retention signals, rotation), shared by server and client. **Cost aggregation happens only in `/api/bi`**: leaders get totals for their team, never individual salaries; only Admin gets per-person salary signals (gap vs. median of same puesto, months without raise); Auditor gets no costs. Salaries in a currency other than `moneda_principal` are reported apart, never converted. Nine Box never assumes "low": people without KPIs or without a row in `evaluaciones_potencial` are listed as "sin clasificar".
- **Bulk import** (header button "📥 Importar", also from the BI "Calidad de datos" card): one workbook with sheets **Áreas → Cargos → Colaboradores** (any may be omitted; a CSV or unrecognized workbook is treated as Colaboradores). `components/importacion/AsistenteImportacion.tsx` (file → column mapping per sheet → review → result). Files are read with `exceljs` in `lib/archivoImportacion.ts` (the old `xlsx` dependency was removed for security — don't re-add it); the template always pre-fills current areas/cargos and its dropdowns point at those sheets. `lib/estructura.ts` (`analizarCarga`) is pure and orchestrates the three sheets (it calls `analizarImportacion` from `lib/importacion.ts` for Colaboradores with the final "virtual" areas/cargos). It runs twice: in the browser for the preview and again in `POST /api/importacion`, which only applies rows the admin confirmed **and** that are still valid server-side, in order niveles → áreas (create, then set parents) → cargos (+ rangos) → colaboradores → area leaders from the Áreas sheet. Rows are matched by email (colaboradores), normalized name (áreas) or área + normalized name (cargos): existing → update (empty cells never erase data), new → create; desvinculados must be reactivated first. `parent_id` cycles from the file are rejected (only the row moving an existing area is flagged).
- **Cargos** (UI word for the `puestos` table — DB/identifiers keep "puesto"; only visible text says "Cargo"): every cargo belongs to an area (`puestos.area_id`, required in the app; legacy rows may be null and are flagged "sin área" until completed), with optional `nivel_id` (→ `niveles_cargo`, configurable per company, ordered) and `descripcion`. Salary ranges live apart in `rangos_salariales_cargo` (admin-only RLS, like `compensaciones`). The same name may exist in different areas; `lib/cargos.ts` (`resolverCargo`) picks the cargo for a person's area (same area → ancestor area → the only other one, with a warning). Managed from "💼 Gestionar cargos" (`components/CatalogoCargos.tsx`). An area with cargos can't be deleted (FK restrict).
- **Duplicate names**: two area/cargo/nivel names are the same if equal after `normalizarNombre` (`lib/similitud.ts`: lowercase, no accents, collapsed spaces), mirrored by `public.normalizar_nombre()` and unique indexes in migration `20261119` — compare names with it, never with `toLowerCase()`. Names that are merely *similar* (`puntajeSimilitud`: Sr/Senior, plurals, typos, acronyms; Junior vs Senior or I vs II are deliberately *not* similar) become "Posibles duplicados" in the import review; the admin must decide each one (unify or create new) before anything is applied, and the server re-validates those decisions.
- **Employee history** (`historial_empleado`) is written **only by DB triggers** (`registrar_historial_empleado` on `empleados`, `registrar_historial_salario` on `compensaciones`) — never insert into it from app code; just update the employee and the trigger records the event. Read it through `GET /api/historial?empleado=ID` (scope-checked; salary events only for Admin), shown by `components/HistorialEmpleado.tsx` in the profile modal and Mi Perfil. `lib/historial.ts` derives retention signals (months in same position, recent manager change, area moves) that `/api/bi` feeds into `senalesRetencion`.
- Migrations can be smoke-tested locally with PGlite (Postgres in WASM): stub `auth.users`, `auth.uid()`, the `authenticated` role and the pre-existing tables, then run `supabase/migrations/*.sql` in order.
- **Performance thresholds are configurable** per company (`configuracion_empresa`, edited from the BI ⚙️ button, served by `/api/datos` as `umbrales`). Use `useUmbrales()` / `coloresDesempeno()` from `lib/umbrales.tsx` — never hardcode 60/70/80/85.
- `lib/servidor/contexto.ts` (`obtenerContextoSesion`) is the shared server entry point: session → perfil → empresa → empleados → `alcance`. New data routes should start from it.
- **Periods** (`lib/periodos.ts`, pure): the management period is the calendar month (`'AAAA-MM'`); "en curso" = current month. KPI `indicadores.periodo` is the *frequency* (shown as "Frecuencia"), not a period: monthly KPIs are evaluated every month; quarterly/semester/annual ones record monthly *avance* and are evaluated in the last month of their calendar window. Each KPI result is stored per month in `resultados_kpi` (one row per KPI + month); `indicadores.resultado_actual/progreso` and `empleados.cumplimiento_general` are the latest values, recomputed by `POST /api/resultados` (the only way to rate a KPI: Admin or the *direct* leader, period not closed, and leaders only until month end + `configuracion_empresa.dias_limite_calificacion`). Don't write KPI results or snapshots from the client.
- **Period closing** (`POST /api/periodos`, Admin, guided UI in `components/periodos/AsistenteCierre.tsx`): only finished months, in order (oldest open first). The server computes the month's compliance from `resultados_kpi` and writes `historico_cumplimiento` rows with `oficial = true` (label like `"Noviembre 2026"`), then inserts `periodos_cerrados`. Official rows are immutable (trigger) and closed months block their `resultados_kpi` (trigger). Rows with `oficial = false` are the automatic monthly *avance*. Reopening: only the last closed month, with a reason (`periodos_reaperturas`).
